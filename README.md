# call-me-maybe


## Description
call-me-maybe is a project for learning how Function Calling works in an LLM (Large Language Model).

Function Calling is a mechanism in which an LLM understands a user's natural-language request, selects an appropriate function from a predefined set, and outputs the parameters required to call it in a structured format.

For example,<br>
for the input<br>
"What is the sum of 2 and 3?"<br>
it generates output like this:
```
{
	"name": "ft_add_numbers",
	"parameters": {
		"a": 2,
		"b": 3
	}
}
```
<br>
This project uses Qwen/Qwen3-0.6B, a small LLM.
A small LLM alone cannot always generate valid JSON or the correct function call.
Therefore, this project implements Constrained Decoding, which constrains the logits of each token output by the LLM, to generate Function Calls that follow the defined JSON structure.
<br>

## Additional Information

### Algorithm explanation

This project implements Constrained Decoding to control the output generated by the LLM so that it follows the specified JSON format.

Normally, an LLM outputs logits for every token in its vocabulary when generating the next token. This implementation restricts generation so that only tokens valid for the current JSON structure can be generated.

The overall process is as follows:

1. Create the context passed to the LLM from the user prompt and Function definitions
2. Convert the context into token IDs
3. Obtain logits for the next token from the LLM
4. Check the current State
5. Determine which tokens can be generated based on the State
6. Change the logits of invalid tokens to `-inf`
7. Select the next token from the valid tokens
8. Update the State based on the generated token
9. Repeat until the Function Call JSON is complete

* JSON generation states are managed by State
```
START
→ FUNCTION_KEY
→ FUNCTION_NAME
→ FUNCTION_SEPARATOR
→ PARAMETERS_KEY
→ PARAMETERS_START
→ PARAMETER_NAME
→ PARAMETER_COLON
→ PARAMETER_VALUE
→ PARAMETER_SEPARATOR / PARAMETERS_END
→ END
```

### Design decisions
The implementation was designed to separate the role of the LLM from the role of Constrained Decoding as much as possible.

The LLM mainly determines:

- The meaning of the user prompt
- Which function to use
- The values to assign to the parameters

The program controls:

- The JSON structure
- Function names present in the Function definitions
- Parameter names present in the selected function
- Token constraints based on parameter types

This design aims to support different prompts and Function definitions without hard-coding functions or parameters for specific prompts.

The code was also divided into multiple files to clearly define the responsibility of each process.

- `models.py`: Definitions of Pydantic models and State
- `preparation.py`: Input data loading and validation, and context creation
- `decoder.py`: Constrained Decoding control based on State
- `decoder_mask.py`: Various masking operations applied to logits
- `validators.py`: Number and string validation
- `state_handler.py`: State transitions after token generation
- `__main__.py`: Overall program execution control
- `token_cache.py`: Encode cache management

Pydantic is used to validate the input data and ensure that Function definitions and prompts have the expected structure.

### Performance analysis:

For the 11 provided test cases, the program generated the correct functions and parameters in every case, achieving 100% accuracy.<br>
It was also confirmed that all outputs could be parsed as valid JSON.<br>
The total execution time for all 11 test cases, measured with `time uv run python -m src`, was approximately 1 minute and 47 seconds, satisfying the requirement of completing within 5 minutes.<br>
Constrained Decoding sets the logits of invalid tokens to `-inf` in each state. Therefore, instead of simply asking the LLM to generate valid JSON, the JSON structure, function names, parameter names, and value types are constrained during generation.<br>

### Challenges faced
One of the most difficult aspects of this project was implementing Constrained Decoding while accounting for the fact that an LLM token does not necessarily represent a single character.<br>
Because one token may contain multiple characters, it cannot be assumed that JSON is generated one character at a time.<br>
Therefore, candidate tokens are decoded into strings, combined with the string generated so far, and evaluated to determine whether they can be allowed.<br>

Determining when to end a number was also difficult.<br>
For example, 144 is a valid number, but it may be followed by a decimal point.<br>
The implementation therefore evaluates “can continue as a number” and “can end as a number” separately. It also allows `,` when parameters remain and `}` for the final parameter.<br>

Determining where strings and regular expressions should end was another challenge. Ending a string too early omits required characters, while failing to end it causes unnecessary text to continue being generated. Token Masking was therefore implemented to check quotation marks, line breaks, and other characters. For regular expressions, `re.compile()` verifies syntactic validity and helps select the ending token.

### Testing strategy
To verify the implementation, the 11 test cases provided with the assignment were tested first, checking that:

* The entire output can be parsed as valid JSON
* A result is generated for every input prompt
* The correct function is selected
* Parameter names and values are correct
* Parameter types, such as number and string, match the Function definition

Additional tests using unseen inputs were performed to avoid relying solely on the provided tests. Different numbers, large numbers, strings absent from the provided tests, and differently worded prompts confirmed that the implementation was not hard-coded for specific samples.

Input handling was also tested with nonexistent files, invalid JSON, and data that did not match the Pydantic models. It was confirmed that the program exits with an error message instead of crashing unexpectedly.

For output, `python -m json.tool` confirmed that it could be parsed as JSON, and each result was verified to contain the three keys `prompt`, `name`, and `parameters`.

Execution time was also measured with `time uv run python -m src`, confirming that the 11 test cases completed in approximately 1 minute and 47 seconds.

### Example usage

The following is an example of running this program.

#### 1. Input files

First, prepare a JSON file defining the available functions.
`data/input/functions_definition.json`

```json
[
    {
        "name": "fn_add_numbers",
        "description": "Add two numbers",
        "parameters": {
            "a": {
                "type": "number"
            },
            "b": {
                "type": "number"
            }
        },
        "returns": {
            "type": "number"
        }
    }
]
```

Next, prepare the user prompt for Function Calling.
`data/input/function_calling_tests.json`
```json
[
    {
        "prompt": "What is the sum of 2 and 3?"
    }
]
```

#### 2. Run the program

Run the following command from the project root directory.

```bash
uv run python -m src \
    --functions_definition data/input/functions_definition.json \
    --input data/input/function_calling_tests.json \
    --output data/output/function_calling_results.json
```

Specify the following files for each option:
- `--functions_definition`: A JSON file defining the available functions
- `--input`: A JSON file containing user prompts
- `--output`: A JSON file where Function Calling results will be written

The program passes the Function definitions and user prompts to the LLM and generates Function Calls using Constrained Decoding.

#### 3. Output
After execution, the results are saved in the file specified by `--output`.
`data/output/function_calling_results.json`

```json
[
    {
        "prompt": "What is the sum of 2 and 3?",
        "name": "fn_add_numbers",
        "parameters": {
            "a": 2,
            "b": 3
        }
    }
]
```
In this example, for the user prompt
```text
What is the sum of 2 and 3?
```
the LLM selects
```text
fn_add_numbers
```
from the Function definitions and generates the required parameters
```text
a = 2
b = 3
```
from the user prompt.

As a result, the natural-language user request is converted into a structured Function Call that can be used by the program.

#### Another example

For example, if the following user prompt is entered,

```json
[
    {
        "prompt": "Greet john"
    }
]
```
and a corresponding function exists in the Function definitions, a Function Call like this is generated:

```json
[
    {
        "prompt": "Greet john",
        "name": "fn_greet",
        "parameters": {
            "name": "john"
        }
    }
]
```
