Introduction
Please adhere to the following rules:

- Remain polite, courteous, respectful and constructive
throughout the evaluation process. The community's well-being
depends on it.

- While interacting with the person (or the group) whose work is evaluated, identify
the possible dysfunctions in their project. Take the time to discuss
and debate any problems you may have identified.

- You must consider that there might be some differences in how your
peers might have understood the project's instructions and the
scope of its functionalities. Always keep an open mind and grade
them as honestly as possible. The pedagogy is only valid
if peer evaluation is conducted seriously.

Guidelines
- Only evaluate the work that is present in the Git repository of the
student or group.

- Double-check that the Git repository belongs to the student
or group. Ensure that the project is the expected one
and also verify that "git clone" is used in an empty directory.

- Check carefully that no malicious aliases were used to fool you
and make you evaluate something that is not the content of the
official repository.

- To avoid any surprises, and if applicable, review together the
scripts used to facilitate grading (such as testing or
automation scripts).

- As an evaluator, if you have not completed the assignment you are
going to grade, you must read the entire subject before
starting the defense.

- Use the flags available on this scale to signal an empty repository,
a non-functioning program, a norm error, cheating, etc.
In these cases, the evaluation process ends and the final grade is 0,
or -42 in case of cheating. However, except for cheating, students are
strongly encouraged to discuss the work that was turned in together,
in order to identify any mistakes that shouldn't be repeated in the
future.

Simple preliminaries

The defense can only occur if the student being evaluated is present. This way everybody improves: by exchanging ideas and sharing knowledge with each other.
Nothing submitted (or wrong file or directory) means 0, and the evaluation process ends.
In order to grade your peer, you have to clone their Git repository on your machine.
Ensure that 10 files (1 per level) are present at the root of the repository. Ensure that they are not empty.
README check

Ensure that a README.md file is present at the root of the repository.
The very first line must follow the required format (italicized): "This project has been created as part of the 42 curriculum by <login...>"
Check that the README contains at least the following sections:
Description — brief overview of the project and goals.
Instructions — how to run the training interface (e.g., run "run.sh"), how to export configs, and what to submit.
Resources — explicit list of resources used to complete the project (training interface, provided files, documentation/references).
AI Usage — clear explanation of whether and how AI was used during the project.
Verify that the Resources section explicitly mentions networking concepts studied, such as:
TCP/IP addressing
subnet mask
default gateway
routers and switches
OSI layers
Verify that the Submission details are stated (10 exported configuration files, one per level, placed at the repository root).
If any of these elements are missing, the evaluation ends now.
Mandatory part
Mandatory Part

This project is about configuring small-scale networks to
make them function properly. You have to download the file attached to the project's page
(the evaluated learner can show you where it is). Then, extract the files and run the run.sh
script.

A page will open in your web browser. In case this does not work, the subject contains a
fallback strategy (once again the evaluated learner can show you).

In case the reviewer is not familiar with networking concepts, check if the README content did
bring enough explanations, otherwise do not hesitate to get into details. It is also possible to
complete the first training level(s) alltogether to settle the fundamental concepts.

During the entire evaluation, the evaluated learner explains their reasonning to
the reviewer.

On the web interface, use the "Evaluation" tab to start the review mode.

In review mode, 3 random levels (from levels 6 to 10) will be automatically presented.
The evaluated learner must correctly solve all 3 levels in a maximum of approximately 15 minutes.
Using the internet or any external resource to find answers is, of course, forbidden.

The use of a simple calculator such as "bc" is tolerated, but that will be the
limit.

You can ask questions about the different levels to the reviewed learner.

簡単な準備

評価を受ける学生が出席している場合にのみ、発表会は実施できます。こうすることで、互いに意見を交換し、知識を共有することで、全員が成長できるのです。
何も提出されなかった場合（またはファイルやディレクトリが間違っていた場合）は0点となり、評価プロセスは終了します。
同僚を評価するには、相手のGitリポジトリを自分のマシンにクローンする必要があります。
リポジトリのルートに10個のファイル（各階層に1つずつ）が存在することを確認してください。また、それらのファイルが空でないことを確認してください。
READMEチェック

リポジトリのルートディレクトリにREADME.mdファイルが存在することを確認してください。
最初の行は、指定された形式（斜体）に従う必要があります。「このプロジェクトは、<login...>によって42カリキュラムの一部として作成されました」
READMEファイルに少なくとも以下のセクションが含まれていることを確認してください。
概要 — プロジェクトの概要と目標を簡潔に説明します。
手順 — トレーニングインターフェースの実行方法（例：「run.sh」の実行）、設定のエクスポート方法、および提出物。
リソース — プロジェクトを完了するために使用したリソースの明示的なリスト（トレーニングインターフェース、提供されたファイル、ドキュメント/参考文献）。
AIの使用状況 — プロジェクトにおいてAIが使用されたかどうか、またどのように使用されたかを明確に説明する。
リソースセクションに、学習したネットワークの概念が明示的に記載されていることを確認してください。例えば、以下のような概念です。
TCP/IPアドレス指定
サブネットマスク
デフォルトゲートウェイ
ルーターとスイッチ
OSIレイヤー
提出物の詳細（リポジトリのルートに配置された、レベルごとに1つずつ、合計10個のエクスポートされた設定ファイル）が記載されていることを確認してください。
これらの要素のいずれかが欠けている場合、評価はここで終了します。
